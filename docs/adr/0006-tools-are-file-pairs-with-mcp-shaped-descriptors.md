# 0006. Tools are separate programs with MCP-shaped descriptors

- Status: Accepted
- Date: 2026-11-09

## Context

A model's capabilities (read a file, fetch a page, run a command) were
already outside the runner as file pairs in `lab/tools/bin/`: an
executable plus a JSON descriptor. Several questions came up while making
the lab installable: which tools ship, whether they should be compiled into
the runner, whether to adopt MCP instead, what language they use, and how a
user could swap one.

## Decision

- A tool is a separate program the runner execs once per call: JSON args
  on stdin, cwd the workspace, combined output as the observation. Neither
  runner contains tool code, and both share one tool set.
- The descriptor uses MCP's tool-definition field names (`description`,
  `inputSchema`), plus lab keys (`runtime`, `sandbox`, `timeout_seconds`).
  MCP itself enters only as adapters at the edges (publishing these tools
  as an MCP server, or wrapping an external server as a tool), never as a
  second path inside the runner. Specs still refuse `mcp:` until an
  experiment demands it.
- `runtime: exe` lets a descriptor name a binary and args instead of a
  script (bin relative to the repo or absolute, never from the model).
- The shipped set is `lab/tools/manifest.json`, generated by
  `scripts/tool-reach --manifest` from reachability plus operator-named
  utilities. Every manifest tool has contract fixtures in
  `tools/bin/<name>.fixtures/`; `scripts/check` fails on an unreachable
  tool, an unfixtured manifest tool, or a non-standard descriptor.
- Tools are Python (standard library only, one pinned interpreter via uv)
  unless there is a reason otherwise. Rust ports live in one multi-call
  binary, `cs-tools`, selected by first argument or `argv[0]`: today
  `fs_read`, `fs_edit`, `okf` and the ops helper `yaml-json`. Ruby is gone:
  stock Ubuntu does not ship it.
- A user replaces a tool by pointing its descriptor elsewhere; the
  sandbox (ADR 0007) bounds what any replacement can do, and run identity
  hashes every tool and helper a run used.

## Consequences

- Any language works; each call is sandboxed and fingerprinted on its own.
- One Rust binary means one build and file to ship, but changing any tool
  in it changes every contained tool's fingerprint.
- A port is held to the original's fixtures. Its parity bar (byte for byte
  or fixtures only) is set per tool with the owner before it starts.
